# Замовлення склопакетів

Невеликий SSR-застосунок для перегляду замовлень склопакетів за тестовим завданням Trainee Frontend.

Стек: React 19, TypeScript, TanStack Start (SSR), TanStack Router, TanStack Query, Mantine, Tailwind CSS, Zod.

Інтерфейс у мʼякому «мальованому» пласкому стилі з живими, ненавʼязливими мікроанімаціями (опис нижче, розділ «Дизайн і анімації»).

## Швидкий старт

Потрібен Node.js 22+ (перевірено на Node 25 і npm 11).

```bash
cd sklores-orders
npm install
npm run dev
```

Відкрити http://localhost:3000, `/` перенаправить на `/orders`.

| Команда             | Що робить                                   |
| ------------------- | ------------------------------------------- |
| `npm run dev`       | dev-сервер з SSR на порту 3000              |
| `npm run build`     | продакшн-збірка в `dist/`                   |
| `npm run preview`   | запуск продакшн-збірки локально             |
| `npm run typecheck` | перевірка типів TypeScript                  |

Імітація збою API для перевірки стану помилки:

```bash
API_FAILURE_RATE=1 npm run dev
```

`API_FAILURE_RATE` це ймовірність від 0 до 1, з якою сервер кидає помилку. За замовчуванням 0.

## Як проєкт створено з нуля (повна ініціалізація)

Якщо треба повторити все самостійно, ось точні кроки.

1. Створити каркас TanStack Start офіційним CLI (React, file-router, Tailwind, TanStack Query):

```bash
npx @tanstack/cli@latest create sklores-orders --framework React --package-manager npm --add-ons tanstack-query --no-examples --no-toolchain --no-git --no-intent --non-interactive
cd sklores-orders
```

CLI ставить: `@tanstack/react-start`, `@tanstack/react-router`, `@tanstack/react-query`, `@tanstack/react-router-ssr-query`, `react`, `react-dom`, `tailwindcss`, `@tailwindcss/vite`, `vite`, `@vitejs/plugin-react`, `typescript`, `@types/react`, `@types/react-dom`, `@types/node`.

2. Поставити UI, форму й валідацію:

```bash
npm install @mantine/core @mantine/hooks @mantine/form zod
```

3. Прибрати devtools, які додав шаблон (вони перекривали шапку і для тестового не потрібні):

```bash
npm uninstall @tanstack/react-devtools @tanstack/react-query-devtools @tanstack/react-router-devtools @tanstack/devtools-vite
```

4. У `tsconfig.json` додати `"resolveJsonModule": true`, щоб сервер міг імпортувати `orders.json`.

5. Покласти `orders.json` у `src/server/data/orders.json` (не в `public/`).

6. Підключити Mantine і Tailwind в одному файлі `src/styles.css` через CSS-шари, щоб preflight Tailwind не ламав стилі Mantine, а утиліти Tailwind могли їх перекривати.

## Чому TanStack Start

- Це саме той стек, з яким працює команда: TanStack Start + Router + Query. Тестове одразу показує, що я можу в ньому працювати.
- Роутинг повністю типізований: параметри (`$orderId`) і search-параметри (`q`, `status`) перевіряються TypeScript, тому посилання на неіснуючий маршрут або неправильний фільтр просто не скомпілюються.
- Search-параметри в URL це «рідна» річ для TanStack Router (`validateSearch`, `loaderDeps`), а не ручна робота з `URLSearchParams`, як у Next.js.
- Серверні функції (`createServerFn`) дозволяють викликати серверний код з лоадера однаково і під час SSR, і під час переходу на клієнті, без окремого `fetch` і ручної серіалізації.
- Серверні ендпоінти (`server.handlers`) живуть поруч зі звичайними маршрутами в `src/routes`.

## Що рендериться на сервері, а що на клієнті

**На сервері:**

- Перший HTML будь-якої сторінки. Лоадер маршруту чекає дані, тож `/orders?q=коваль&status=new` приходить уже відфільтрованим, а `/orders/1005` з таблицею позицій і підсумками.
- HTTP-статуси: неіснуючий id (`/orders/9999`, `/orders/abc`) і будь-яка невідома адреса віддають сторінку «Не знайдено» з кодом `404`. Збій даних на сторінці замовлення дає `500` зі сторінкою помилки.
- Редірект `/` → `/orders` (307).
- Читання `orders.json`, фільтрація за пошуком і статусом, створення нового замовлення, штучна затримка 300–800 мс.
- Дані з кешу TanStack Query передаються на клієнт разом з HTML (`@tanstack/react-router-ssr-query`), тож після гідрації немає повторного запиту.

**На клієнті:**

- Переходи між сторінками після першого завантаження (лоадер викликає ту саму серверну функцію через RPC).
- Пошук з debounce 300 мс і фільтр статусу: вони оновлюють URL, а TanStack Query тримає попередній результат на екрані, поки вантажиться новий.
- Сортування таблиці (теж через URL, але без нового запиту: сортується вже отриманий список). Під час SSR той самий код сортує список на сервері, тож `/orders?sort=total&dir=desc` одразу приходить відсортованим.
- Стани завантаження, помилки й порожнього результату.
- Форма «Нове замовлення»: валідація і перерахунок вартості під час введення.
- Перемикання теми.

Розрахунок вартості це чисті функції в `src/lib/pricing.ts`, вони однакові для сервера і клієнта, тому SSR і гідрація дають однаковий результат.

## Як сторінки отримують дані

Є два шляхи до одних і тих самих функцій з `src/server/orders.server.ts` (`findOrders`, `findOrderById`):

1. **HTTP-ендпоінти** для зовнішніх клієнтів:
   - `GET /api/orders?q=&status=` повертає відфільтрований список. Невідомий `status` дає `400`.
   - `GET /api/orders/:id` повертає замовлення або `404` з `{ "error": "Замовлення не знайдено" }`.
2. **Серверні функції** (`src/server/orders.functions.ts`) для самих сторінок.

Сторінки використовують серверні функції, а не `fetch('/api/...')`, тому що:

- під час SSR не треба робити HTTP-запит сервера самого до себе і знати його абсолютну адресу;
- типи відповіді беруться напряму з функції, без ручного парсингу JSON;
- вхідні дані перевіряються Zod-схемою на сервері (`validator`);
- під час переходів на клієнті та сама функція викликається через RPC автоматично.

Затримка 300–800 мс стоїть всередині спільних функцій, тому вона є і в ендпоінтів, і в серверних функцій, і в сторінках.

У списку лоадер на сервері чекає дані (`prefetchQuery`), а на клієнті не блокує перехід: URL змінюється одразу, а компонент показує попередній результат напівпрозорим і спінер біля заголовка. Так поле пошуку не втрачає фокус і не перемонтовується під час введення. Сторінка замовлення навпаки чекає дані в лоадері (`ensureQueryData`), бо тільки так сервер може віддати справжній `404`.

## Розрахунок

Усе рахується в цілих числах, щоб не ловити похибки `0.1 + 0.2`:

- площа зберігається в мм² (`width × height`), а не в м²;
- мінімум до оплати 500 000 мм² (0,5 м²) за одну штуку;
- вартість позиції рахується одразу в копійках: `площа_до_оплати_мм² × ціна / 10 000` з округленням до найближчої копійки (половина вгору);
- вартість замовлення це сума вже округлених вартостей позицій;
- площа показується з двома знаками, але вартість рахується з точної площі.

Чому це важливо, видно на замовленні **1016**: позиції коштують 6 753,375 і 1 083,875 грн. Після округлення кожної позиції це 6 753,38 + 1 083,88 = **7 837,26 грн**. Якщо округлити тільки суму, вийде 7 837,25, що неправильно за формулою з ТЗ.

Формат грошей `7 660,00 грн`, площі `4,56 м²`, дат `ДД.ММ.РРРР` у часовому поясі Києва (щоб сервер і браузер в іншому поясі показували ту саму дату). Між розрядами і перед «грн» стоїть нерозривний пробіл, щоб сума не розривалась на два рядки.

## Сортування списку

Клік по заголовку будь-якої колонки (№, дата, клієнт, статус, позицій, вартість) сортує за нею за зростанням, повторний клік за спаданням. Активна колонка позначена стрілкою ↑ або ↓, неактивні блідою ↕. Сортування зберігається в URL (`?sort=total&dir=desc`), не скидається при пошуку, фільтрі і кнопці «Скинути фільтри», переживає перезавантаження. За замовчуванням сортування за номером за зростанням, тоді параметрів в URL немає.

Статуси сортуються за ходом роботи (Нове → В роботі → Виконано), а не за алфавітом. Клієнти за українським алфавітом. При однакових значеннях порядок визначає номер. Логіка в `src/lib/sort-orders.ts`.

Пошук також враховує різні апострофи (`'`, `’`, `ʼ`), регістр, зайві пробіли і символи `#` або `№` перед номером.

## Форма «Нове замовлення»

Сторінка `/orders/new`. Поля: клієнт, телефон, позиції (тип скла, ширина й висота 100–3000 мм цілими числами, кількість від 1). Позицій може бути кілька, вартість кожної й загальна перераховуються під час введення. Та сама Zod-схема перевіряє дані у формі (через `schemaResolver` з `@mantine/form`) і ще раз на сервері.

**Де зберігається:** у пам'яті серверного процесу (масив у `src/server/orders.server.ts`, який стартує з копії `orders.json`). Нове замовлення одразу з'являється в списку, у пошуку і на сторінці `/orders/:id`, а також у `GET /api/orders`.

**Обмеження цього способу:**

- після перезапуску сервера всі нові замовлення зникають, файл `orders.json` не змінюється;
- у dev-режимі сховище може скинутись після гарячого перезавантаження серверного файлу;
- на serverless-хостингу (Vercel, Netlify) кожен інстанс має свою пам'ять: замовлення, створене в одному, може не знайтись в іншому, і зникне, коли інстанс засне;
- немає блокувань, тож при одночасному створенні з кількох процесів номери можуть повторитись;
- дані бачать усі користувачі, авторизації немає.

Для справжнього продукту тут потрібна база даних. Для тестового цього достатньо, і на відміну від `localStorage` нові замовлення проходять через ті самі серверні ендпоінти та SSR.

Типи скла для форми сервер збирає з наявних замовлень (5 типів).

### Телефон

Номер приймається в будь-якому звичному вигляді, а зберігається завжди в одному форматі `+380XXXXXXXXX`. Під полем видно, як саме номер буде збережено. На сторінці замовлення він показується як `+380 67 111 22 33`.

Дозволені символи: цифри, пробіли, дужки, дефіси, крапки і `+` на початку. Що приймається (усі варіанти стають `+380671112233`):

| Ввели | Як розпізнано |
| --- | --- |
| `+380671112233`, `380671112233`, `+380 67 111 22 33`, `380-67-111-22-33` | 12 цифр з `380` |
| `+38 (067) 111-22-33`, `38 067 111 22 33` | 12 цифр з `380` |
| `067 111 22 33`, `(067) 111-22-33`, `067.111.22.33`, `0671112233` | 10 цифр з `0`, додаємо `+38` |
| `8 067 111 22 33`, `80671112233` | 11 цифр з `80`, додаємо `+3` |
| `67 111 22 33`, `671112233` | 9 цифр без `0` на початку, додаємо `+380` |

Не приймається: менше або більше цифр (наприклад `380 848 9328` має лише 10 цифр, `+380` і ще 7), літери, `+` не на початку, `+` перед номером без коду країни (`+067…`), 9 цифр з нулем на початку (`067111223`, швидше за все пропущена цифра). Логіка в `src/lib/phone.ts`, та сама Zod-схема працює і у формі, і на сервері.

## Темна тема

За замовчуванням тема як у системі (`defaultColorScheme="auto"`), плюс перемикач у шапці. Вибір зберігається в `localStorage`. `ColorSchemeScript` від Mantine стоїть у `<head>` і виставляє атрибут `data-mantine-color-scheme` до першого малювання, тому світла тема не блимає. Tailwind `dark:` прив'язаний до цього ж атрибута через `@custom-variant`, а іконка перемикача перемикається через CSS, тож немає розбіжності між SSR і гідрацією.

## Дизайн і анімації

Стиль: теплий «паперовий» фон, пастельні заливки (мʼята, персик, лаванда, масло), темне обведення 2 px з трохи нерівними кутами, пласкі тіні-«наліпки» без розмиття. Без градієнтів і світіння. Темна тема має ті самі пастелі, приглушені.

Шрифти (Google Fonts): **Nunito** для інтерфейсу й цифр (округлий, табличні цифри, кирилиця) і **Caveat** (рукописний) для заголовків і приміток.

Анімації зроблені на чистому CSS і Web Animations API, без бібліотек:

- рядок замовлення при наведенні або фокусі з клавіатури мʼяко заливається зліва направо пастеллю свого статусу (лаванда для «Нове», масло для «В роботі», мʼята для «Виконано»), піднімається, справа зʼявляється стрілка;
- рядки списку зʼявляються каскадом; при сортуванні та фільтрації рядки плавно переїжджають на нові місця (FLIP-анімація в `src/lib/use-flip-animation.ts`);
- стрілка сортування повертається, у мобільній версії замість заголовків є кнопки сортування;
- кнопки й поля пружно реагують на наведення, фокус і натискання;
- статус «В роботі» має крапку, що тихо пульсує;
- перемикач теми крутить сонце в місяць;
- заголовки підкреслені «від руки», лінія домальовується при відкритті сторінки;
- у формі позиції «вискакують» при додаванні, вартість легенько підстрибує при кожній зміні, помилки валідації «хитають» головою;
- позиції, що оплачуються як 0,5 м², позначені рукописною приміткою «мін. 0,5 м² за шт»;
- порожній список, замовлення без позицій, помилка і 404 мають мальовані дудли, що плавно гойдаються;
- під шапкою під час переходів «бігає» олівцева лінія завантаження.

Усі анімації вимикаються, якщо в системі ввімкнено «зменшити рух» (`prefers-reduced-motion`).

## Адаптивність

На ширині 360 px сторінки не мають горизонтального скролу. Список замовлень на телефоні перетворюється на картки, таблиця позицій прокручується всередині своєї картки, фільтри й поля форми стають у колонку.

## Деплой

Ще не задеплоєно. TanStack Start збирається під будь-який хостинг з SSR. Найпростіше: Netlify або Vercel, підключити репозиторій, команда збірки `npm run build`. Для конкретного хостингу CLI вміє додати адаптер (`--deployment netlify|vercel|nitro`). Обмеження сховища в пам'яті на serverless описані вище.
